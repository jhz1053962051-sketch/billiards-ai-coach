# 台球 AI 教练

三个能力：

1. **击球求解**——给定球局，告诉你**打哪颗球、进哪个袋、瞄哪里、用多大力**，并给出这一杆**允许偏多少度**。直接路线打不了时，会算组合球、翻袋、以及把母球藏起来的防守。
2. **打一整局**——标准黑八 15 颗球或九球 9 颗球，按 WPA 规则开球、分组、判犯规、续杆，一杆接一杆打下去；轮到你时给建议，**轮到对手时它自己打**。可以存档、撤销，也能手调力度杆法自己打。练习模式可手动记录真实球桌上的进球结果，设置每日 5/10/20 杆目标，给未进球标注原因，查看命中率趋势与连续练习天数，导出 CSV 分析或下载完整 JSON 备份并在确认后恢复；系统会根据最近 20 次未进的标注原因，谨慎提示可练的专项，原因样本不足或分散时不会武断判断。每个容错区间至少 20 次记录后才显示 Wilson 95% 统计区间，且仅作训练参考，不会自动修改 AI 推荐。记录只保存在本机，不会把仿真演示算成实战成绩。
3. **动作评估**——给一段视频或一张照片，逐项判断**你的击球动作哪里不规范**，并明确告诉你**哪些项这次测不出来**。

练习模式提供直线球、切球和长台球三类一键摆球专项训练，每次开练轮换六种合法球位与目标袋方向，减少固定摆位带来的记忆偏差。每组 5 杆至少命中 4 杆即达标；训练进度与实战记录一样只保存在本机浏览器。

纯 JavaScript（ES modules），**零运行时依赖**，无构建步骤。物理核在 Node 测试和浏览器页面里跑的是同一份代码。姿态检测用 MediaPipe Pose Landmarker（Apache-2.0），模型与 wasm 已随仓库放在 `vendor/pose/`，不需要联网。

```bash
node tools/start.mjs        # 起服务 + 打开浏览器，一条命令
```

`tools/start.mjs` 是幂等的：服务已在跑就只开浏览器，端口被别的程序占用会明确报错而不是静默失败。想分开控制时：

```bash
node tools/serve.mjs        # 只起服务，然后手动打开 http://127.0.0.1:4173/
                            #   /demo/            击球求解 / 打一局
                            #   /demo/pose.html   动作评估
node tools/test.mjs         # 跑测试（等价于 npm test）
node tools/status.mjs       # 开机自检：服务、两个页面、控制台报错（等价于 npm run status）
node tools/verify-all.mjs   # 三项门禁一次跑完（等价于 npm run verify）
```

`verify-all.mjs` 按顺序跑单元测试 → 演示页静态检查 → 浏览器端到端，「三项全过」以前靠人记，漏掉的那次恰好是改坏了东西的那次。它自己起一个临时静态服务（端口现取，不占 4173），跑完收尾，最后只打一句结论和一个退出码。端到端那步要启动 Chrome，必须在放得开命名管道的环境里跑。

`serve.mjs` 只开放 `/demo`、`/src`、`/vendor` 三个目录，也只认 `127.0.0.1` 与 `localhost` 这两个 Host。它是本机开发用的服务器，不是发布用的：仓库根上的 `.git/`（完整提交历史）、`_research/`（素材）、`.deepseek-harness/`（会话记忆）都不该被一个 GET 读走，所以按目录白名单拦在最前面，路径里出现以点开头的段（`.git`、`..`）直接 403。畸形编码（比如 `/%`）回 400，不会把进程带走——之前这里一次 `decodeURIComponent` 抛异常就能让服务退出，任意网页放一个 `<img src="/%">` 就够。

`tools/test.mjs` 会按当前 Node 版本挑进程隔离开关——这个开关改过两次名字（22.8 的 `--experimental-test-isolation=none`、23.6 起叫 `--test-isolation=none`），写死在命令里就只能在某一段版本区间用。

`tools/status.mjs` 和 `tools/verify-demo.mjs` 的分工：后者是逐项验收（133 项断言，改代码后跑），前者只回答「现在这一刻系统能不能用」——五条路由是否 200、两个页面是否真加载、求解是否出结果、控制台有没有报错。改完代码想知道有没有把页面弄坏，跑 status 十几秒就够；要验收细节才跑 verify-demo。

浏览器调试端口原来是写死的（verify-demo 9333、`cdp.mjs` 的 `launch()` 9450、verify-pose 9461）。端口被占时 Chrome 起不来，但脚本照样去连那个端口——连上的是**别人家的**调试服务，于是验收脚本可能对着另一个浏览器里的别的页面一路全过。现在统一用 `freePort()` 现取一个空闲端口，导航后再核对 `location.origin` 确实是目标地址，防止重定向到别处还能假通过。

两个页面都带了 CSP（`<meta http-equiv="Content-Security-Policy">`），`script-src` 只放 `'self'`，`object-src 'none'`。这台机器上的页面从不联网，也没有一处内联脚本或 `onclick`，把这条允许写死没有代价；写了之后哪天某个 import 里混进一段外链脚本，页面会直接拒绝执行而不是安静跑下去。`style-src` 留了 `'unsafe-inline'`，因为正文用了 46 处 `style="..."` 内联样式，收紧就得先把它们全挪进 `<style>`，对本地演示页不划算。`pose.html` 多两个必要例外：`'wasm-unsafe-eval'`（CSP 一旦写了 `script-src`，哪怕没有 `'unsafe-eval'`，WebAssembly 编译也会被拒，模型直接加载失败；这个关键字只放开 wasm 编译）和 `media-src 'self' blob:`（用户选的视频是 `URL.createObjectURL` 出来的 blob 地址，少了它 `<video>` 会安静地停在「`loadeddata` 永远不来」，看着像卡死）。`check:demo` 会断言两个页面的 CSP 都在、`script-src` 只放 `'self'`、没有 `'unsafe-eval'`，并在 wasm 页面里存在 `'wasm-unsafe-eval'`。

CSP 只写在 `<meta>` 里，`frame-ancestors` 在 meta 中会被浏览器忽略——要防套框得靠响应头，本机开发服务器没做。这是刻意的取舍，写在这里免得被当成「已经防住了」。

## 为什么做这个

市面上绝大多数「台球瞄准器」回答的是「这一杆能不能进」——把假想球位置算出来，画一条线就完事。但打球的人真正需要知道的是**这一杆有多稳**。

这个差别不是措辞问题。`ctbot000/three-cushion-billiards` 的 README 里有一组实测数据（三库球，随机布局）：

| 排序方式 | 瞄准窗口（中位数） | 同样执行误差下的命中率 |
|---|---|---|
| 按「能不能进」取第一杆 | 0.04° | 12% |
| 按「容错窗口」重排 | 0.58°（最大 1.6°） | 68% |

0.04° 是任何人类都打不出来的精度。按「能不能进」排序，等于推荐一堆理论上成立、实战中必然打丢的球。

所以本项目的排序键是 **`aimToleranceDeg`（容错窗口）**，不是进球与否。每个候选方案都会输出「±0.57°」这样的数字——**这是你能接受的瞄准误差上限**，而不是装饰。

在容错窗口之上还有一层**走位修正**。只按这一杆的难度排序会漏掉一件事：同样能进的两个袋，母球打完停的位置可能差出十几分难度。实测 79 个有多候选的布局里，**65% 的情况「这一杆最容易」≠「下一杆最好打」**，改按下一杆排序平均能让下一杆难度低 **12.4 分**。加上修正后，在能对比出下一杆难度的布局里，有 12 次选杆因此改变，其中 **11 次下一杆更好、1 次更差**。

所以每个候选额外算一个 `leaveScore`（0–100，由打完之后的台面反推下一杆的容错窗口），综合价值 = 单杆难度 − 走位修正，修正双向封顶 ±22.5 分。只要打完仍有合法目标球，求解器会比较不同力度/杆法下的实际仿真母球停位，输出母球路线、建议停位及下一杆目标；下一杆越难，推荐排序惩罚越大。

### 物理核（`physics.js`）

球的状态是 `(x, y, vx, vy, wx, wy, wz)`——两个线速度、两个滚动角速度分量、一个绕竖直轴的塞。核心是**滑动期与滚动期分开积分**：

- 台呢接触点的滑移速度 `u = (vx - R·wy, vy + R·wx)`。
- `u ≠ 0` 时球在打滑，摩擦沿 `-u` 方向，减速度 `muSlide·g`；同时滑移按 `3.5·muSlide·g` 的速率衰减，`tRoll = |u| / (3.5·muSlide·g)` 后进入纯滚动。
- 纯滚动后减速度降到 `muRoll·g`（约打滑期的 1/20），球能滚得远得多。

碰撞用**事件驱动**：每步算所有库边与球对的 TOI（time of impact），只推进到最早的那个接触点，解决它，再继续。这样不会因为球速快而穿库。库边冲量分法向（恢复系数随入射速度略降）与切向（受库边摩擦与滚动耦合限制），球球碰撞同样分法向与切向——**切向冲量就是「甩球」（throw）的来源**，也是薄球容易打丢的物理原因。

### 求解器（`solver.js`）

对每个「目标球 × 袋口」组合：

1. **反解接触法线**。不是简单地把假想球放在「目标球 → 袋」的反向延长线上——那样忽略了甩球。`solveContactNormal` 用不动点迭代反解一个法线方向，使得加上甩球偏移后目标球**实际**出球方向对准袋心。实测 45° 切球时甩球量约 **2.3°**，不补偿就是直接打丢。
2. **算容错窗口**。袋口捕获半径减去球半径得到横向余量，换算成母球端的角度容差。
3. **解析反解力度**。目标球要滚到袋口需要多少末速度 → 除以碰撞传递系数 → 母球撞击瞬间速度 → 反解出杆初速（考虑打滑期损耗）。
4. **用真实物理核试打**。在克隆的世界上真的跑一遍，`target.pocketed && target.pocket === pocketId` 才算通过。不通过就扫力度（10 档）× 微调瞄准角（±0.15°/±0.3°/±0.45°），全都失败就淘汰这个候选。

第 4 步是关键。只靠解析解的推荐杆，在随机布局上的成功率是 **65.4%**；加上仿真验证后是 **100%**（197/197）。一次仿真约 0.8 ms，验证十几次也就十几毫秒——完全付得起。这就是「能进才留下」和「算出来就推荐」的差别。

### 性能：从 23 ms 降到 8 ms

求解是整局里唯一的耗时大头（占 95% 以上），所以优化全在它身上。每一处都是先量、再改、改完复量，没有一处是「看着像瓶颈」。

| 改动 | 求解 p50 | 依据 |
|---|---|---|
| 起点 | 23.17 ms | 基线，`_research/probe-optimize-1.mjs` |
| `pocketAt` 去掉开方 | 16.45 ms | 单次求解调它 167553 次，命中 18 次（0.011%） |
| `Math.hypot` → `Math.sqrt` | 11.51 ms | 2000 万次微基准：hypot 451 ms、sqrt 276 ms，慢 1.6 倍 |
| 求解器步长对齐执行步长 | **8.22 ms** | 见下 |

`pocketAt` 原来是每个袋口算一次 `Math.hypot(dx, dy)` 再和捕获半径比。改成先比外接正方形（四次减法、四次比较，不开方），再比平方距离。这不是近似——「`|d| ≤ r`」和「`dx²+dy² ≤ r²`」在双精度下是同一件事，台球坐标（< 4 m）也远不可能溢出。改完 CPU profile 里 `pocketAt` 从 28.9% 掉到 0.2%。

`Math.hypot` 有溢出保护（内部要判断量级再缩放），对台球完全用不上——速度上限 6.6 m/s、角速度上限几十 rad/s，平方和离双精度上限差十几个数量级。`advanceBall` 里的两处 `Math.hypot` 换掉之后，这个函数（占物理核 39%）的耗时直接降了三分之一。

### 一个隐蔽的不一致：验证用的步长比执行还细

`rules.js` 的 `simulateShot`（真正打出去的那一杆）用 `SEARCH_DT = 1/120`，而求解器的 `trialShot`（验证能不能进）原来不传 `dt`，走的是 `runShot` 默认的 `FIXED_DT = 1/240`。

**验证比执行更精确不是优点。** 验证的意义是预测实际会发生什么，精度对不上时它预测的是另一件事：求解器用 240 Hz 算「这一杆能进」，用户点下去按 120 Hz 真的打，两边算出来的球位不是同一个。改成一致之后既修掉了这个问题，求解还快了一倍。

改完之后还有个遗留问题：页面和对手那边把 `1 / 120` **写死**在五个地方（`demo/app.js` 四处、`src/opponent.js` 一处）。它们此刻恰好等于 `SEARCH_DT`，但哪天有人只调了 `constants.js` 里的那个常数，这五处不会有任何提示——又一次「验证和执行算的不是同一件事」。现在全部改成 `import { SEARCH_DT }`，并且 `check:demo` 加了一条静态断言：`src/` 与 `demo/` 里除 `constants.js` 之外，任何一处出现 `1/120` 字面量都报错。

### 步长不能随便调粗

`settlePockets` 只在子步结束时看球心位置，所以「一子步位移 < 捕获半径」是它正确工作的前提。pool9 台最小捕获半径 63.0 mm，最高球速 6.6 m/s：

| 步长 | 一子步位移 | 余量 |
|---|---|---|
| 1/240 | 27.5 mm | 2.3× |
| 1/120 | 55.0 mm | 1.15×（能用的最粗值） |
| 1/60 | 110 mm | 超过捕获半径 |

失效方向和我一开始猜的**相反**。不是「快球穿过袋口不算进」，而是「擦袋角的球被误判成进袋」——一子步跳得太远，球直接越过库边落进捕获圆。实测 6.6 m/s、纵向偏 64 mm 打右下袋：1/240 判不进（正确），1/30 判进（错）；扫 4 种力度 × 41 个偏移共 **8 处**这种误判。

修法是在 `stepWorld` 入口按当前最快球速把步长钳到 `0.9 × 63 mm / v`。**两次尝试都写进了热循环，两次都更慢**：用 `Map` 存每球起点 → p50 7.74 → 9.10 ms；把起点记在球对象的 `__px/__py` 上 → 10.78 ms（给球对象加新字段会改 V8 隐藏类，`advanceBall` 里所有属性访问一起退化）。这个函数每杆跑几百次，任何每子步的工作都会被放大。放到入口做一次，热循环里一行都不用加，代价是零。

**这里踩了个自己写的坑**：第一版钳制写在 `let remaining = dt;` 之后，于是钳制算出来的 `dt` 谁也没用上。探针显示「开关钳制结果完全一样」时才发现——测试当时也是绿的，因为那条测试的正向断言本身就在测一个不会失败的方向。现在 `test/physics.test.js` 里那条用例是反向验证的：关掉钳制它必须失败。

### 难度评分与走位修正

```
单杆难度 = 0.55 × 容错窗口分 + 0.25 × 切角分 + 0.2 × 距离分  (+18 若有摔袋风险)
走位修正 = clamp((leaveScore − 50) × 0.45, −22.5, +22.5)
综合价值 = 单杆难度 − 走位修正
```

容错窗口权重最大，因为它最能预测人类是否会打丢。切角与距离是次要修正。

`leaveScore` 由「打完之后的台面」算出：对剩下的每颗合法目标球 × 每个袋做几何筛查（假想球在不在台内、两条路径通不通、切角 ≤82°），取容错窗口最大的那个当「下一杆有多好打」。若仍有合法目标球，求解器会继续试不同力度与高/低杆，按真实仿真的母球停位选出下一杆容错更大的版本；结果同时给出母球停位、实际走位轨迹和下一杆目标，供球桌叠加显示。没有后续目标球时不为无意义走位增加击球力度。

#### 这套分数准不准：实测校准

分数好看不代表说得准。所以做了一轮端到端校准（`_research/probe-calibration-e2e.mjs`、`probe-difficulty-order.mjs`、`probe-sigma-sweep.mjs`）：随机布局 → `solveShot` → 取排序第一的候选 → 在它的 `aimAngle` 上叠正态误差 → 用真实物理核打，统计进袋率。

**排序是对的。** 同一布局内比较「难度最低」与「难度最高」两个候选，69 组对比里 **69 组（100%）** 难度低的确实更容易打进，平均命中率 83.1% vs 19.2%，差 64 个百分点；整个候选池（404 个）的 Spearman ρ(难度, 实测命中率) = **−0.885**，Pearson r = **−0.899**。所以 `difficultyOf` 的权重不需要推翻。

**但档位名有隐含前提。** 按档位统计真实命中率，扫描不同的瞄准误差 σ：

| σ | 很容易 | 容易 | 中等 | 偏难 |
|---|---|---|---|---|
| 0.10° | 99% ✓ | 94% ✓ | 85% ✓ | 83% ✓ |
| 0.20° | 97% ✓ | 82% ✓ | 63% ✓ | 43% ✓ |
| 0.30° | 94% ✓ | 69% ✗ | 47% ✗ | 37% ✓ |
| 0.60° | 80% ✗ | 46% ✗ | 29% ✗ | 13% ✗ |

判定下限（写死在探针里，不事后调整）：很容易 ≥85%、容易 ≥70%、中等 ≥50%、偏难 ≥30%。结论是**这套档位只在 σ ≲ 0.2° 时诚实**。0.2° 的含义是 1 米外偏 3.5 毫米、2 米外偏 7 毫米——练过的人的水平，不是新手。

所以档位名不能单独出现。`solver.js` 导出 `LABEL_SIGMA_DEG = 0.2` 与 `difficultyCaveat()`，UI 的 `#verdict`、`#gVerdict`、备选行全部带上「按瞄准误差 ±0.2° 估算」，页面上还有一行常驻说明。测试钉住这件事：`coach()` 的 verdict 里必须同时出现档位名和这条前提，且 `LABEL_SIGMA_DEG` 落在 (0, 0.5] 内。

#### 卡片上的数字也要说人话

「容错 ±0.57°」和「母球建议停位 (1.62, 0.83) 米」这两句话，写的人知道自己在说什么，站在台边的人不知道。0.57° 和 0.2° 在纸上差三倍，落到手上是「偏 8 毫米」和「偏 3 毫米」——后者基本等于打不进；坐标更没法用，没人会在台子上比划 `x = 1.62`。

所以 `solver.js` 导出了两个把数字翻成人话的函数：

- `toleranceText(c)` → `容错 ±0.57°（母球走 1.37 米，方向偏 4 毫米就打不进）`。换算用 `tan(容错) × 母球到假想球的距离`，也就是这一杆真正要走的路。贴球（不到 20 厘米）时这个换算会退化成「偏 1 毫米」，没有信息量，就只给角度。
- `cueRestText(table, rest)` → `母球建议停位：台面右下（距右库 12 厘米）`。九宫格说位置、到最近那条库的距离说精度，能直接对着台子找。没带球台的旧调用方退回坐标而不是抛异常。

候选对象上带一份球台（`c.table`），因为 `describeCandidate(c)` 只吃一个参数；测试钉住「不许退回坐标」这条。

**另外查清一个不是缺陷的现象。** `difficultyOf` 的三个分项理论上限并不齐（`tolScore` 能到 100，`cutScore` 切角 80° 才满且 >82° 被门槛挡掉，`distScore` 要母球到假想球 2.6 m 才满而实测 p90 只有 56.8）。但这不构成问题：全量 2345 个候选的档位分布是 9.5% / 30.4% / 37.8% / 18.7% / 3.3% / 0.3%，六档都有样本，且排序正确率 100%。之前以为「档位严重偏软」是采样偏差——只取首推方案，而求解器当然优先推荐简单的（160 个首推里 86 个「很容易」）。

## 打一整局（`src/rack.js` + `src/rules.js`）

演示页的「打一局」标签页是一个可以真的打下去的黑八对局，不是单杆演示。

### 三种选杆，目标函数各不相同

| 情形 | 用什么算 | 目标 |
|---|---|---|
| 开球 | `solveBreak` | 把球堆打散，让 ≥4 颗目标球碰库（WPA 4.3d / 5.3b） |
| 有球可进 | `solveShot`（含组合球、翻袋） | 进袋 + 容错窗口排序 |
| 都进不了 | `solveSafety` | 把母球藏起来，让对手接手后更难打 |
| 连防守都赢不过正撞 | `solveDirectHit` | 先碰到合法球，保证这一杆不犯规 |

把这几者分开而不是塞进一个函数加 `if (isBreak)`，是因为它们的目标函数**根本不同**：15 颗球挤成三角阵时没有任何一颗有通往袋口的通路，拿「能不能进」去搜必然返回空；开球真正要满足的规则是「没进球时至少四颗目标球被驱向库边」。

### 组合球与翻袋

两者都只在**直接解一个都没有**时才计算（`solveShot` 的 `opts.extras`），因为成本高得多：组合球要枚举中间球 × 目标球 × 袋并各做十几次仿真，翻袋要先把目标球当单球跑仿真（实测 3.19 ms/组）。

- **组合球**是两级假想球：`G_B = B − 2R·û(P − B)`（A 的球心要到达的点）、`G_A = A − 2R·û(G_B − A)`（母球球心要到达的点），两级都过 `solveContactNormal` 把甩球算进去。容错取两级里更窄的那个——误差会串联。思路参考 [bfjesso/pool-shot-calculator](https://github.com/bfjesso/pool-shot-calculator)（MIT）的链式假想球，代码是自己写的。
- **翻袋**用袋口镜像当种子，再交给仿真修正。**镜像绝对不能直接当解**：实测库边反射比镜面偏 2°–4°，塞加到 0.2 时偏到 7.6°，而袋口容错只有零点几度。所以流程是「镜像给种子 → 单球仿真迭代修正出球方向 → `solveContactNormal` 反解母球 → 整台仿真验证」。

难度上，组合球固定 +12、翻袋固定 +18。翻袋本来可以照 [tomasz-pawlaczyk/Poolgame-AI-shot-prediction](https://github.com/tomasz-pawlaczyk/Poolgame-AI-shot-prediction)（**无 LICENSE，只读思路**）那样用 8×/4× 的**乘数**，但乘数会让容错很小的翻袋直接冲满 100 分，反而看不出「翻袋之间也有好坏」，所以折成加数。

翻袋这条路上踩了三个坑，都是「代码看着对、结果恒为空」的那种：

1. **切角算成了恒定 90°**。切角要相对「目标球翻库后的出球方向」量，代码却把 `target` 自己当成袋口传进去，于是 `V.sub(target, target)` 是零向量、`acos(0)` 恒等于 90°，78° 的门槛把**所有**翻袋候选都筛掉了。表现是 `describeCandidate` 的翻袋分支写得好好的、`difficultyOf` 的 +18 也写好了，但永远没有候选能走到那里。
2. **尝试配额把后面的袋饿死**。`maxBanks` 本意是「最多产出几个候选」，却同时被用来数「尝试了几次」，而且被拒的尝试也算一次。袋口按 `c-bl → c-br → c-tl → c-tr → m-b → m-t` 顺序遍历，第 10 次尝试落在 `c-tl` 上，**下中袋永远轮不到**。修法是把 `maxBanks`（成功数）与 `maxBankTries`（尝试数）拆成两个上限。
3. **容错按直线路径算，翻袋比正对直球还宽松**。`aimToleranceDeg` 收的是「目标球到袋口的距离」，翻袋直接传了真实袋口，可球要先撞库再弹回来，实际路径长了一倍多。结果容错被算成 **±1.95°**（正对直球才 ±0.12°），难度只有 37，排序时会排到正经球前面。修法是传**镜像点**——`dist(target, 镜像点)` 正好是展开后的直线长度，这就是标准几何里的「展开路径法」。修完容错变成 ±0.05°、难度 73.9。

三条都有对应的测试钉住：切角不再恒 90°（翻袋候选真的出现了）、放宽配额不会让结果变少、翻袋容错落在 (0, 1.2) 度内。

### 防守（`src/safety.js`）

六七个同类开源项目里**没有一个实现防守**（pooltool 的 `ruleset/` 只做合法性与状态推进；tailuge/billiards 的 `strategies/` 全是找袋；henshmi 的 `AIPolicy.evaluate` 把球间距求和**最大化**，方向与防守相反），所以这块是从文献式子落地的：Smith《Running the Table》(AAAI-06) 的「只在根节点生成防守分支 + 从对手视角评估」，和 CUECARD (IJCAI-09) 的 `v_LR = v_CC − v_OPP`（**差值**，不是绝对值）。

做法：枚举「合法目标 × 9 档瞄准偏移 × 4 档力度」，每杆真跑一次 `runShot`，再用 `positionTolerance` 算对手接手后的容错窗口。

**打分必须是差值，这是本项目踩过最实的一个坑**。第一版按「对手接手后容错有多小」的绝对值打分，5 个布局里 2 个挑出来的「防守」反而让对手更容易打了（±0.15° → ±0.33°、±0.16° → ±0.21°，打分却分别是 92 和 95）。根因很简单：**绝对值奖励的是「这张台子本来就难」，不是「我把局面弄难了」**。改成与基准杆（正对最近合法球、中力）比差值后，同一批布局 5/5 全部真的改善。

**瞄准偏移必须按几何上界缩放，不能写死角度——这是第二个坑。** 第一版写的是固定角度 `[0, ±10, ±20, ±30, ±42, ±55]`，看着很合理，其实绝大多数采样点根本碰不到球。几何上界是 `d·sin θ ≤ 2R`：pool9 的 `2R = 57.15 mm`，于是

| 母球到目标球 | 最大可用偏移 |
| --- | --- |
| 0.5 m | 6.56° |
| 1.0 m | 3.28° |
| 2.0 m | 1.64° |

1 米开外，10° 及以上一律碰不到球。实测九球真实局面 44 组采样里：**29 组完全没碰到**（白跑一整杆仿真）、9 组是母球先撞库弹回来才碰到的（碰到的还不是目标球，不由这一杆决定，评分却在奖励它）、真正「直接碰到、可控」的只有 6 组，**占 14%**。

改成 `swingOffsetsDeg(distToCue, R)`：按上界的比例 `[0, ±0.35, ±0.62, ±0.82, ±0.94]` 采样，0 是正对、越接近 1 切得越薄。同一批布局的可控率 **14% → 75%**，撞库兜底的样本 **9 → 0**。九个防守布局实测全部仍有解且全部真的改善局面（打分 81.9–96.4）。

**这条测试差点写成假的。** 第一版断言「`solveSafety` 返回的偏移不超过几何上界」，但 `frac = 0`（正对球心）时偏移恒为 0，永远满足上界——把实现改回固定 55° 之后测试照样通过。修法是把采样策略本身导出来（`swingOffsetsDeg`）单独断言「每个采样点都在上界内**且最大值达到上界的 80% 以上**」，再加端到端「三种距离都必须找到解、且打出去真的碰到 1 号球」。反向验证：把 `f * bound` 改成 `f * 55` 后，这条测试报 `AssertionError: 距离 0.35 m 的采样偏移 19.250° 超过了几何上界 9.398°`，改回来即通过。

还有个兜底：`if (!best || best.safetyGainDeg <= 0) return null;`——赢不过基准杆就不算防守，`planShot` 会退回兜底直撞（而兜底直撞本来就是那杆基准）。

只在**一颗都进不了**时才防守，不做「进攻机会一般时也防守」。Smith 的 `t0 = 65%` 门槛需要可靠的进球概率估计，而这里的 `difficulty` 是难度分不是概率，硬套门槛会把「偏难但该打的球」误判成该防守。界面上有开关，关掉就退回纯兜底。

`solveDirectHit`（兜底直撞）用的是同一套几何：偏移 `[0, ±5, ±10, ±16, ±24, ±35]` 里，1 米距离上同样有 18% 是空跑。这个没改——它的采样只有 22 组、单次仿真 0.27 ms，全跑一遍 6.2 ms，实测已经很快；而改它要重排「撞完之后球跑了多远」的评分口径，风险大于收益。

### 规则实现范围

**黑八**，按 WPA 规则（2026 版第 4 节 + 2021 IEPF 第 4/6 节）实现：

- **开球**：母球在开球线后；没进球时至少 4 颗目标球碰库，否则判 `ILLEGAL_BREAK` 并重摆；开球进 8 号不犯规，重摆回 8 号点。
- **分组**：开球不分组、台面 open；open 时先碰 8 号是犯规（除非本组已清完）；分组由第一颗合法进球决定，一杆进两组时按**母球先碰到的那颗球**定。
- **犯规**：母球落袋、未碰球、先碰对方球、碰球后无球碰库（进袋也算碰库）。
- **续杆**：进本组的球继续，否则换人。犯规换人 + 对手持球（开球犯规限开球线后）。
- **胜负**：本组清完后合法进 8 号胜；提前进 8 号、与最后一颗本组球同杆进 8 号、进 8 号同时犯规，都判负。
- **连续犯规**：只记账，**不判负**。

最后那条要说明一下。本项目早先按「三次连犯判负」实现，后来查 WPA 3.13 原文才改掉：

> "In games scored by the Rack, such as 9-Ball, the fouls must be in a single Rack. **Some games such as 8-Ball do not include this rule.**"

规则原文明确把黑八排除在外。

**九球**，按同一份 WPA 规则第 5 节（生效日 2025-09-15）实现，与黑八的差别不只是摆球：

- **摆球**：菱形 1-2-3-2-1，9 颗。1 号在顶点、**朝球台头端**；**9 号在菱形正中、压在底点（脚点）上**。其余七颗随机。
- **先碰**：每一杆母球必须先碰到**台面上号码最小**的那颗球（3.2）。
- **胜负**：合法进 9 号即赢局，不必清完。唯一例外是开球不达标却进了 9 号——那颗要摆回来（Regulation 16(5)）。
- **回位**：只有 9 号会回位（被犯规打进、或开球不达标打进）；其余球一律不回位。
- **开球有两条门槛，性质不同**：(b) 没进球时至少 4 颗目标球碰库，不达标是**犯规**；(c) 「进袋 + 越过开球线」的球合计少于 3 颗是**「非法开球」，不是犯规**——接手方可以照打或把这一杆交回（Regulation 16）。
- **三犯**：同局内连续三次犯规判负，且第二次犯规时要先提醒（未提醒则第三次只按第二次算）。
- **不分组**，也没有 open 概念。

摆球这条踩过一次坑，值得记下来：一开始照抄黑八的「顶点压脚点」，但 WPA 5.2 原文是

> "the 1-ball at the apex of the diamond towards the head of the table and **the 9-ball in the middle of the diamond and on the Foot Spot**"

——压在脚点上的是菱形正中那颗 9 号，顶点在它前面两排。两个游戏的规矩正好相反。这个错误是端到端验证抓出来的（断言「9 号 x ≠ 脚点」时才发现 9 号根本不在正中）。

同一个错误还牵出了第二个 bug：开球方案原来按「离 8 号点最近的球」找顶点球，在黑八三角阵里正好是顶点，但在九球菱形里那正是 9 号球——于是开球建议变成「照着 9 号瞄」。改成「离母球最近的那颗」后两个玩法都对。

**不做的部分**（`src/rules.js` 文件头也写了）：不实现叫袋（两个玩法都不叫袋；九球 5.4 的推杆也不做）；不实现需要杆头轨迹才能判的犯规（推杆、连击、球未停就击球等）；不处理球离台；不实现僵局重开；不合法开球只给「对手重摆」（黑八）与「照打 / 交回」（九球）。

### 对手出杆（`src/opponent.js`）

轮到对手时它自己打，玩家不用替它点按钮。关键决定是**不写第二套 AI**：`takeTurn()` 内部调的就是玩家点「求解 + 打这一杆」时跑的 `planShot` / `simulateShot` / `resolveShot`，参数完全一致。这样「对手会不会打」和「玩家能不能打」是同一个问题，不会出现两套逻辑慢慢走偏。

三个实现细节值得说明：

- **不改入参**。`takeTurn` 先 `cloneGame`，包括持球摆位在内都发生在副本上，返回 `next` 新对象。所以界面可以先播动画、播完再装回新局面——动画期间 `state.game` 仍是旧局面，球位不会被提前改掉。
- **持球自己摆位**。`pickCueSpot` 用网格采样（12×8，跳过边界）挑**离所有目标球最远**的合法空位，而不是 `findFreeSpot` 的「螺旋找到第一块空地就停」——后者很容易把母球塞在球堆边上。开球线后持球时先按 `headStringX` 裁掉线前的点。采样要求离最近球 ≥ 直径 + 1 mm，否则 `placeCueBall` 会把它推开、位置就不受控了。
- **回报 `cueSpot`**。`placeCueBall` 内部仍可能微调落点，所以 `takeTurn` 返回的是它**实际**停在哪，不是请求点。界面和测试都读这个字段——读 `next.balls` 里的母球是错的，那已经是打完之后的球位了。

已知简化（写在文件头）：只在一颗球都进不了的时候才防守（见上一节说明为什么不做「进攻机会一般时也防守」）；不会为了走位放弃已经验证能进的球；持球只挑最远空位、不做位置优化。所以它是「会打进球并兼顾下一杆的练习伙伴」，不是「会下棋的对手」。

界面上有个「对手自动出杆」开关，关掉就退回双方都由人操作——留着是因为调试规则时常常需要手动替对手打一杆。

### 撤销

球局面板有「撤销上一杆」，最多退 20 步。实现是**每杆结算前存一份 `cloneGame` 快照**，撤销就是把整份局面装回去。

顺序不能反：`resolveShot` 不改入参（它返回新的 `next`），所以在结算前传进去的 `g` 正好是这一杆**之前**的局面；先结算再存就退错一步。对手那条路径同理——`takeTurn` 内部先 `cloneGame`，打完之前的 `g` 还是原样。

撤销还有个容易漏的地方：**在途的动画和定时器**。对手续杆之间隔了 450 ms 再出下一杆，动画回放也是异步的；这期间用户可能撤销、开新局、换台，等回调醒来时 `state.game` 已经不是它算的那一局了，装回去就把新局覆盖成旧的。所以 `state.generation` 每换一次局面就 +1，回放回调和续杆定时器醒来先核对局号，对不上就直接返回。

一次真实的踩坑：端到端测试里撤销后杆数从 1 跳到 11——上一段测试留下的对手续杆定时器在新局上继续出杆，一路把杆数推了上去。局号就是为解决这个加的。

### 球台切换与玩法切换

标题旁有两个下拉：**球台**（中式八球 9 尺 / 美式八球 8 尺 / 斯诺克 12 尺）和**玩法**（黑八 / 九球）。尺寸与球半径在 `src/constants.js`，页面上的选项由它动态生成——只维护一份数据，不在 HTML 里抄第二遍。

换台会重摆、清空撤销栈、作废在途动画。渲染层的 `createRenderer({ canvas, table })` 里 `table` 是 `let` 而不是参数解构的常量，因为 `toPx` / `toWorld` / `fit` 全都依赖台面尺寸；`setTable(next)` 只换引用，调用方随后必须重新 `fit()`，否则缩放比还是旧台的。

球台和玩法是两个独立的下拉，可以组合——斯诺克台打九球是允许的，只是球变大了相对台面更小、更容易进。**斯诺克玩法没有实现**，它只是一个台面尺寸。

### 摆球

黑八用 `rackLayout` 摆标准三角阵：顶点球在脚点（`length × 3/4`），8 号在第三排正中，两个底角一全色一花色。九球用 `rackDiamondLayout` 摆菱形：1 号在顶点、9 号在正中且**压在脚点上**。`createRack(kind, table, opts)` 按玩法分发，界面与测试都走这个入口。**认不出的玩法直接报错，不回落黑八**：原来写成 `kind === 'nineball' ? 九球 : 黑八`，于是 `'snooker'`、中文 `'九球'`、拼错的 `'nine-ball'` 全都会被静默摆成黑八，一局球按另一套规则跑完也不会有任何提示。不传 `kind` 仍然算黑八，那是正常默认值；`createGame` 同样处理。玩法登记表 `GAME_KINDS` 放在 `rack.js`（那边零依赖），`rules.js` 转出去，两边共享一份名单。

`seed` 决定其余球的排列，同 seed 可复现。`rackLayout(table, [3, 5, 9])` 可以只摆指定的几颗——练习模式的「加一颗」用的就是这个。

**全色与花色怎么排。** 这里有两种规则，本项目都核对过：

| 来源 | 原文 | 结论 |
|---|---|---|
| WPA 2026 §4.2 | "The other balls are placed in the triangle without purposeful or intentional pattern." | 其余球随机，不作有意排列 |
| CBSA《中式台球比赛规则》（大师赛版） | "其它目标球要尽量使花色和全色尽量分开，但必须彼此紧贴。" | 全色与花色尽量岔开 |

两者都合规。本项目按 CBSA 那种做——不是为了合规，而是随机摆出来的三角阵经常出现同排三颗全色相连，玩家一眼就看出「这不是标准摆法」。

具体用哪一套组别分布不是随便挑的。三角阵 15 个球位之间共有 **30 条相贴边**（球心间距恰为 2R 的相邻对）。在「8 号在第三排正中 + 两底角一全一花」这两个硬约束下，穷举全部 1848 种合法组别分布（`_research/rack-bruteforce.mjs`，另有独立回溯实现 `_research/rack-optimal.mjs` 交叉验证），**同组相贴的边数最少就是 7 条**——不是近似，是可证明的下界。达到这个下界的摆法有 60 个（含镜像）。

代码里的 `RACK_PATTERN` 就是其中一个：

```
    S
   S T
  T 8 S
 S S T T
S T T S T
```

`sameGroupEdges()` 可以验算任意组别分布的相贴边数，测试里对 40 个 seed 逐一断言结果恒为 7。号码在各自组内洗牌、模板与其左右镜像由 seed 随机选，所以每次摆出的球不同，组别分布始终最优。

实测对比：改之前随机打散的平均是 **38.3%** 的相贴边同组（10 个 seed 里最差 16/30），改之后 10 个 seed 全部是 **7/30 = 23.3%**，且同排最长连排从 3 降到 2。

九球菱形是三角阵去掉四个角，所以相贴边是 **16 条**（不是 30 条）。`NINE_ADJACENCY` 原来是按「行优先」的三种偏移硬编码的，算出来只有 14 条——因为菱形每排是**居中**的、相邻两排错开半格。改成按坐标判（`yIdx = j − (countOf(row) − 1) / 2`，相邻两排相贴当且仅当 `|yIdx 差| = 0.5`）之后才是对的。

### 手动出杆

练习模式给了四个滑块：力度、瞄准偏移、高低杆、左右塞，加一个「按这个打」按钮。求解器的推荐值可以用「用求解器的参数」一键灌进去，之后再手动微调。

关键在于 `state.manual.touched`：滑块一旦被用户动过，求解结果就不再覆盖它。否则每点一次「求解」就把人刚调好的力度冲掉，滑块等于没用。

求解器本身仍然**从不使用左右塞**（`tip.a` 恒为 0），但手打时可以自己加——这是「求解器不做」和「用户不能做」的区别。

### 力度槽（`getPowerTier()`）

力度不是只显示一个数字。`demo/app.js:1335` 的 `getPowerTier(speed)` 把 0.55–6.60 m/s 线性映射成百分比，再切成四档，每档有自己的颜色、徽章渐变和光晕：

| 档位 | 百分比 | 速度范围 | 含义 | 颜色 |
|---|---|---|---|---|
| 轻力 | 0–29% | 0.55–2.31 m/s | 细腻走位、贴库过渡 | 翡翠绿 `#10b981` |
| 中力 | 30–59% | 2.31–4.15 m/s | 标准走位、常规进球 | 晴空蓝 `#0ea5e9` |
| 发力 | 60–84% | 4.15–5.66 m/s | 长台推进、强力拉杆 | 琥珀金 `#f59e0b` |
| 爆杆 | 85–100% | 5.66–6.60 m/s | 强力冲球、极限爆裂 | 炽烈红 `#ef4444` |

档位划分是照着 8 Ball Pool / 腾讯桌球的习惯来的，不是随便切的：轻力上限 29% 对应「球刚好够走一库」，85% 以上对应「开球那种不要命的冲」。

这个档位不只影响文案，还直接驱动球杆的后拉位移：`updateManualLabels()` 里 `state.manual.strokeOffset = tier.ratio * 0.12`。所以点 100% 芯片时球杆往后拉 0.12 m，点 25% 时只拉 0.03 m——第一人称视角下能直接看出力度大小。端到端验证里有四项专门钉这个契约（DOM 完整、100% 读作爆杆、25% 读作轻力、后拉位移随力度单调）。

垂直拉杆槽本身（`powerMeterTrack` / `powerMeterFill` / `powerMeterHandle`）也能直接拖：`initPowerMeterEvents()`（`demo/app.js:1967`）按指针 Y 坐标反算速度——`ratio = 1 - (clientY - rect.top) / rect.height`，再线性映射回 0.55–6.60 m/s 并量化到 0.05 的整数倍。和滑块双向同步，拖动时会置 `state.manual.touched = true`，所以求解结果不会再覆盖它。

### 第一人称视角

`viewToggle` 按钮在「俯视」和「第一人称趴杆」之间切换。相机用临界阻尼弹簧连续改变高度、朝向和构图；切换中途反向时会保留当前速度，不会突然刹停再启动。第一人称构图把母球留在可击打区域；桌身厚度、木纹和台呢织纤维按桌面坐标投影，避免运镜时材质随画面漂移。击球回放会累计球的行程，让条纹和号码盘随滚动旋转，停球后保留最终朝向。

渲染侧对应的是 `render.js` 里的 `camera.t`（0 = 俯视，1 = 完全趴平）。它不是简单地切换两套画法，而是**按 t 连续变形**：`computeCurrentCamera()`（`demo/render.js:163`）用瞄准角和母球位置算出相机空间，台面多边形经过近平面裁剪（`clipPolygonNear`），库边、袋口、球、球杆都跟着做透视投影。所以运镜过程中台面是真的在转，不是淡入淡出两张图。

几个按 t 分段触发的细节，都是「太早出现会穿帮」：球杆在 `t > 0.12` 才淡入（`drawCueStick`，`render.js:876`），瞄准 HUD 在 `t > 0.22` 才出现（`draw1stPersonHUD`，`render.js:1001`），背景在 `t > 0.02` 开始渐显。第一人称下球杆还会按 `strokeOffset` 往后拉，配合上面的力度档位。

### 存档

球局面板的「存档 / 读档 / 删档」把局面写进 `localStorage`（键 `pool-ai-coach/game/v1`）。`demo/save.js` 只存**局面**：球位、轮次、分组、犯规数、持球状态、玩法和球台；**不存对局日志与撤销栈**——前者是给人看的流水，后者最多 20 步且只在当前页面内有意义，塞进去只会让存档体积与校验复杂度一起涨。

读档走的是完整校验 `sanitize()`：球台 id 得认、每颗球的坐标得是有限数、号码 0–15 且不能重复、至少要有一颗没落袋的母球、玩家人数得是 2。任一不过就返回 `null`，界面报「存档读不出来」而不是装一个半坏的局面进去。存档来自用户随时可改的 `localStorage`，不能假设它是对的。

读档还会**跟着存档换台与换玩法**——存档是 8 尺九球，读进来就是 8 尺九球，不会把球摆在错的台面上。

### 键盘

`S` 求解、`Enter`/空格 打这一杆、`Z` 撤销、`N` 新局、`1`/`2` 切模式、`←`/`→` 瞄准偏移 ±0.1°、`↑`/`↓` 力度 ±0.1 m/s。

有一处必须处理：**焦点在输入框、下拉或滑块上时不抢按键**。方向键在 `<input type="range">` 上本来就是调值，全局监听一拦，滑块就废了。`isTypingTarget()` 检查 `INPUT`/`TEXTAREA`/`SELECT`/`contentEditable`，命中就直接返回。端到端测试里有一项专门验证这点（聚焦滑块后按 `↑`，力度不变）。

## 动作评估（`src/pose/`）

输入一张照片或一段视频，输出 12 项检查的逐项结论。**照片只判站姿 7 项**（出杆是动态的，单帧无从谈起），**视频判全部 12 项**。

### 12 项检查与参考区间

站姿（单帧）：

| 检查项 | 参考区间 | 怎么量 |
|---|---|---|
| 站姿宽度 | 1.0–2.2 × 肩宽 | 两脚（脚尖点）距离 ÷ 肩宽 |
| 前臂垂直 | 0–15° | 握杆手前臂偏离竖直的角度 |
| 架桥臂伸直 | 152–180° | 肩—肘—腕的肘角 |
| 躯干前倾 | 38–78° | 髋中点→肩中点的连线与竖直的夹角 |
| 屈膝 | 142–174° | 髋—膝—踝的膝角 |
| 头低位 | 0.02–0.55 × 躯干长 | 鼻低于肩线的垂直量 ÷ 躯干长 |
| 头在杆上方 | 0–0.38 × 肩宽 | 鼻到「两腕连线」的水平距离 ÷ 肩宽 |

出杆（需要视频序列）：

| 检查项 | 参考区间 | 怎么量 |
|---|---|---|
| 出杆直线度 | ≤ 0.02 偏差/行程 | 触球前握杆手轨迹对主轴的垂直偏差 ÷ 行程 |
| 掉肘 | ≤ 0.075 × 躯干长 | 触球前肘关节的下沉量 |
| 头身稳定性 | ≤ 0.14 × 肩宽 | 出杆全程鼻的最大位移 ÷ 肩宽 |
| 送杆长度 | 0.3–1.5 × 击球前行程 | 触球后手继续走的距离 ÷ 触球前的行程 |
| 出杆节奏 | 1.3–4.2 后摆:前摆 | 后摆时长 ÷ 前摆时长 |

阈值来自 Dr. Dave 的 Pool Fundamentals「Best Practices」Check List（公开教练检查表），不是凭空设的。**但没有在真实台球视频上做过统计标定**——所以每条结论都带置信度，界面必须显示。

出杆分段靠速度：钟摆出杆在**触球瞬间速度最大**，所以速度峰值就是触球点。峰值之前是后摆与前摆，之后是送杆。前摆和送杆方向相同，只能靠速度分开。

### 两个诚实性机制

这套东西最容易犯的错不是算错，是**把模型噪声当成你的动作缺陷**。所以有两道闸。

**一、测量死区。** 对 `_research/cand/` 里 17 张真实台球照片做水平镜像后重跑模型，再把坐标还原，比较同一个物理量的两次读数。这 7 项指标全是关节角、比值、平面距离，对整体左右反射严格不变——人的姿态没变，读数变了就只能是模型噪声。实测 `|Δ|` 中位数：

| 指标 | 噪声 | 判定区间宽 | 噪声/区间 |
|---|---|---|---|
| 站姿宽度 | 0.223 × 肩宽 | 1.2 | 0.19 |
| **前臂垂直** | **19.5°** | **15°** | **1.30** |
| 架桥臂伸直 | 13.9° | 28° | 0.50 |
| 头低位 | 0.032 × 躯干长 | 0.53 | 0.06 |
| 躯干前倾 | 5.2° | 40° | 0.13 |
| 屈膝 | 10.0° | 32° | 0.31 |
| 头在杆上方 | 0.186 × 肩宽 | 0.38 | 0.49 |

复现脚本 `_research/flip-stability.mjs`。结论：**前臂垂直这一项单张照片根本测不准**（噪声比判定区间还宽），界面会标「单目易失真」，只给趋势不给结论。其余项落在区间外时，偏离必须超过 2 倍噪声才认，否则判「测不准」而不是「不规范」——差得还没噪声大，判了就是猜。

**二、证据覆盖率门槛。** 加权总分只在测到的权重占比 ≥ 45% 时才给。低于 45% 一律返回 `score: null` / 「无法评估」，界面明说「只测到 N% 的项目，证据不足，不给总分」。

这条不是保守，是必须的：一张裁到膝上的合影，双脚 visibility 只有 0.49–0.57，只剩「头低位」和「躯干前倾」两项能测，加权算出来是 8 分「需要从头改动作」。这是拿 2 项证据冒充 7 项结论。同样地，覆盖率低于 70% 时档位文案会加限定词（「测到的部分很规范」而不是「很规范」）——只测到一半就说很规范，和什么都没测到却给 0 分是同一种不诚实，只是方向相反。

### 还有一道取景检查

MediaPipe 的关键点是**回归**出来的，肢体被画面裁掉时它照样给坐标，visibility 还可能高到 0.99。实测一张脚被裁掉的照片，模型把两只脚摆到相距 1.32 米（4.2 倍肩宽），看起来像「站姿过宽」，其实人根本没拍全。所以每项检查先看参与计算的关键点在归一化画面坐标里离边界有多远，贴边（< 0.5%）就判「有肢体被裁掉了，这一项不判」，并提示重拍。

### 视频比照片准在哪

准备阶段人体基本静止，帧间差异主要是模型噪声。把这段的多帧姿态平均，噪声按 1/√n 下降——12 帧平均后噪声降到 1/3.5。**这是视频相对照片的真正价值**，也是为什么视频模式的覆盖率通常高于照片。

### 已知局限（动作评估）

- **单目相机只有投影**。所有角度都在 MediaPipe 的 `worldLandmarks`（做过人体尺度归一）里算，比像素稳，但仍有上表的噪声。前臂垂直一项基本不可用。
- **阈值是参考区间，未做统计标定**。真实教练的判定会比这套规则更宽松或更严格，取决于个人风格。
- **不支持多人**（`numPoses: 1`，取画面里最显著的那个人）。
- **不判杆法**（高低杆/加塞）。球杆不是 MediaPipe 的关键点，看不出打点。
- **不做击球结果判定**。动作规范 ≠ 球一定进；这两件事在本项目里是分开的两个模块。

## 已知限制（击球求解与球局）

- **只有 2D**。没有跳球、没有球离台、没有 3D 旋转可视化。
- **防守只会藏、不会「做斯诺克」**。它枚举瞄准偏移与力度并评估对手接手后的容错，但不做多层规划（不打「这一杆给下一杆做球、下一杆再防守」的组合）。也不做「进攻机会一般时也防守」——理由见上方防守一节。
- **规则只覆盖能从事后事件流判定的部分**。推杆、连击、球未停就击球这类需要杆头轨迹的犯规判不了；不叫袋；不处理僵局重开；九球 5.4 的推杆也不做。
- **杆法建议是经验规则**，不参与排序。求解器给你的杆法里 `tip.a`（左右塞）恒为 0——它从不主动使用侧旋；`tip.b`（高低杆）按切角与距离三档切换，只影响文案不影响排序。手打时可以自己加塞。
- **组合球与翻袋只在没有直接解时才算**。成本高（翻袋要先把目标球当单球跑仿真），直接解存在时它们排不到前面，也就不值得算。
- **袋口模型是圆形捕获区 + 袋角夹球**，不是真实袋口的斜角几何。对容错窗口的量级是对的，对贴库薄球的细节会有偏差。曾经在捕获圆外再叠一层指向袋心的"袋口吸力"去模拟袋口弧度，但那个近似没有任何校准数据，还会把贴库平行滚过中袋的球直接吸进袋、和捕获圆判定重复，实测让两条袋口回归测试挂掉，已删除——要更接近真实，得按袋角实际形状做接触求解，而不是加一个吸力。
- **只有两种玩法**。黑八与九球是完整的；**斯诺克玩法没实现**——换到斯诺克台打的仍是黑八或九球规则，只是台面尺寸变了。
- **对手不会下棋**。它用的是玩家那套求解器 + 同一个防守模块，没有多层规划、不会为了下一杆放弃这一杆的进球。所以它是练习伙伴，不是会算很多层的高手。
- **存档只在同一个浏览器里**。写的是 `localStorage`，换机器、换浏览器、清缓存就没了。也没有导出/导入文件。
- **两个标签页会各打各的**。存档只有一份，后存的盖先存的。现在第一次覆盖前会拦一下、把对方存到第几杆说出来，再点一次才真覆盖；但它不会把两边合并，也不会自动把另一边的局面读进来（正打到关键一杆时突然换桌，比丢一份存档更糟）。
- **没有音效**，也没有触屏手势（单指拖动球能用，但没有双指缩放）。
- **动作评估要 WebGL2 + wasm SIMD**（见上方「系统要求」）。主页面不依赖这些。

- 站姿 7 项（教科书姿态全 good 且满分；**单改一个部位只有对应项掉档**；无 world 坐标只返回一条说明；visibility 过低判 unknown；脚出画判 unknown）
- 出杆 5 项（后摆/前摆/送杆切点顺序正确；匀速平移不算一杆；波动检出直线度问题；掉肘、头身晃动、送杆不足各自可检出）
- 测量可靠性（死区生效、噪声缩放、**已 unknown 的项不被死区说明覆盖原因**）
- 汇总（unknown 从总分剔除不当 0 分、issues 按严重度排序、覆盖率不足不给分、档位限定词、多帧平均真的降低噪声）
- 端到端（真实形状的 PoseLandmarkerResult → 报告；完全没检测到人不崩）

有三条测试是全部可信度的支点：求解器那条不是检查「函数返回了个数」，是检查「**推荐的那一杆真的能进**」；规则那条不是检查状态字段，是检查「**推荐的方案真打出去不犯规**」；防守那条不是检查「算出了分数」，是检查「**防守后的局面真的比正撞更难打**」。

## 端到端验证

三个脚本，都用 Chrome DevTools Protocol 真开一个浏览器。

```
node tools/status.mjs          # 开机自检：服务 + 两个页面 + 控制台（约 15 秒）
node tools/verify-demo.mjs     # 击球求解 + 加球 + 打一局
node tools/verify-pose.mjs     # 动作评估：图片 / 真实录像 / 静止反例 三条路径
```

`status.mjs` 和另外两个不是一回事，先说清分工：它是「现在这一刻系统能不能用」，另外两个是「改动有没有破坏既定契约」。前者检查五条路由是否 200、两个页面是否真加载、求解是否出结果、控制台有没有报错；后者是 127 项断言。改完代码想知道有没有把页面弄坏，跑 status 十几秒就够。

`status.mjs` 写的时候踩了一个 CDP 的坑：**别用 `Target.createTarget` 新建标签页**。第一版照着「干净隔离」的想法先建一个新 target 再 `Target.attachToTarget`，结果 `Target.createTarget` 直接超时 30 秒——Chrome 从 `/json/list` 拿到的那个 page target 已经可以直接 `Page.navigate`，多绕一层反而挂在会话建立上。现在的写法是连现成 target、`Runtime.enable` / `Log.enable` / `Page.enable` 之后 navigate，和 `verify-demo.mjs` 一致。

`verify-demo.mjs` 除了点按钮，还会读 canvas 像素统计「画了多少」「台呢绿占多少」，防止空白页假通过。它在导航前先探一下 `DEMO_URL`：静态服务没起就直接打印「先运行 `node tools/serve.mjs 4173`」并 `exit 2`，不会退化成一句误导人的 `Cannot read properties of null`；导航后再确认 `#table` 与 `window.__app` 都在，缺一个就带着页面自报的错误退出。它跑 133 项检查，分二十二段：file:// 兜底（**直接双击打开要有提示、不能说白屏就白屏**）、练习模式（**开机首屏的状态行不许被清空** → 求解 → **难度档位带精度前提、页面上有常驻说明、** → **求完解状态行要换成「点『进了』或『没进』」** → 切备选 → 演示进球 → **记完一杆按钮仍可点、双击不记成两杆、同一个球位能连记**）、回放被打断（**回放中点重置、切模式都不能把球位写脏**、2 颗球的训练题在回放中重置成 4 颗不许崩）、加球（摆满 16 颗 → 单加一颗条纹球 → **拿掉一颗** → 拿光后按钮禁用）、球局（**先关掉「对手自动出杆」把变量控住** → 建局 → 求解 → 打一杆 → **连打三杆确认局面真的在推进**）、对手（**再把开关打开** → **自动出杆** → 不点任何按钮连打 → 轮到对手时点「求解」必须被挡住）、撤销（开局按钮是灰的 → 打一杆后可撤销 → **撤销后杆数真的退回打之前** → 空栈时不动局面）、拿掉球（下拉只列台上目标球、不含母球 → 拿光后禁用）、换台（三张台 → **缩放比跟着变** → 斯诺克台能开球）、九球（切玩法 → **9 号压在底点上** → 开球打顶点 1 号 → 先碰最小号）、防守（造死局 → **真的给出防守且对手容错被压下来** → 关掉开关退回兜底）、存档（保存 → 读回 → 玩法与球台跟着回来 → **把带 `onerror` 的名字写进存档，读回来必须当文字画出来**）、手动出杆（拖滑块 → 值进 `state.manual` → 标签跟着更新）、力度槽（**点 100% 芯片读出爆杆、点 25% 读出轻力，且球杆后拉位移随力度变小**）、键盘（切模式 → 微调 → **聚焦输入框时不抢键**）、额外解（**页面上真能求出翻袋与组合球**，且文案各自说清是哪种）、第一人称（切视角 → 加上 `fpv` 类 → 切回去掉）、窄屏（**真的把视口压到 390×844，不许出横向滚动、不许有元素越出右边、「求解最佳方案」与「打一局」必须整个在视口里**——页面里有 `@media` 就等于声称手机上能用，这种声明最容易在改主布局时悄悄烂掉）、姿态页窄屏（同一套 390×844，量的是姿态页的 `#stage` 与 canvas **是不是真有宽度**：这页原来是「左画面右面板」、侧栏固定 390 px，手机上侧栏一个人吃掉整行，主画面被压成 0 宽——实测 48 px / canvas 0；而这页的现实输入恰恰是手机拍自己出杆，所以必须适配）、收尾（**全程没有未捕获异常**——有些崩溃发生在某段断言之后，比如回放的 tick 要等帧放完才走到回调，只能靠这条兜住）。

换台那一段有个和直觉相反的地方：**不能拿 canvas 的像素宽度判断换台成功**。画布是按可用宽度自适应缩放的，三张台在同一个窗口里都是 1060px 宽，真正变的是 `view.scale`（9 尺 378.6、8 尺 424、12 尺 276.8）。第一版断言写成比较像素宽，于是「切了台但看起来没变」——不是代码错了，是断言测错了东西。

撤销那一段还有个坑：**必须先排空上一段留下的对手续杆定时器**。对手连打那段结束时可能还排着 450 ms 的 `setTimeout`，直接 `newGame()` 会让它在新局上接着出杆，杆数一路飘到 11。现在的做法是先关掉「对手自动出杆」开关、等这条链自己看到开关停下，再开新局。（就算漏了这一步，`state.generation` 也会兜住——局号对不上就直接返回，不会再打。）

对手那段有一处要说明清楚：**「连打」是合成的**。每轮脚本显式把轮次设回对手，只验证界面侧的链路（`maybeOpponentTurn` → `takeTurn` → 回放 → 结算 → 再问一次「还是对手吗」）能连续跑通；对手进不进球是概率事件，靠它自然续杆会让这项检查时灵时不灵。「对手真的能把局打完」由 Node 侧的整局测试覆盖。

防守那段也走过一次弯路：第一版造的死局在浏览器里仍然有直接进球机会，于是求解器照打进攻、`hasSafety` 一直是 `false`，这一整段等于没测到防守。后来换成 `_research/probe-safety.mjs` 里那个「四颗球挤成一团」的布局（进攻候选 0 个）才真正走进去，实测输出 `防守：打 1 号球（正对） · 轻力 · 中杆（防守不加塞） · 对手容错从 ±1.66° 压到 ±0.00°`。

额外解那一段也是同样的坑，而且踩得更隐蔽：**读错了字段**。第一版写的是 `state.solution.all`，但 `coach()` 返回的卡上只有 `best` 和 `alternatives`，没有 `all`，于是 `kinds` 恒为空数组、两条断言假失败——不是翻袋算不出来，是断言取错了地方。第二版还发现组合球的布局选错了：练习模式不传 `allow`，台上任何球都能打，那个布局里 1 号球本身就有直线解，`extras` 根本不会启动。换成「球挤在左下角」（`cue (0.5L, 0.5W)`、`1 号 (0.08L, 0.10W)`、`9 号 (0.14L, 0.14W)`）之后才真的走到组合球分支，实测 `组合球：打 9 号球撞 1 号球进左下底袋 · 两级切角最大 22° · 容错 ±0.38°`。

`verify-pose.mjs` 的三条路径各自钉一个契约：

1. **图片**（`_research/cand/s01.png`，全身可见的斯诺克站姿照）→ 模型加载、7 项站姿、DOM 与内存一致。
2. **真实录像**（`_research/vid/41903.mp4`，Mixkit 免费素材）→ 出杆真的切出来了、5 条动态检查真的产出、站姿做了 12 帧平均、滑杆能拖。素材缺失时会明确报「跳过」而不是假装通过；跑 `node _research/fetch-videos.mjs` 可下载。
3. **静止反例**（页面内合成，画面里没人出杆）→ 必须只返回 1 条「没识别出出杆」的 unknown，**不许从噪声里硬凑 5 条结论**。

注意：Chrome 的多进程模型要创建命名管道，在受限沙箱里会以「拒绝访问」失败，需要在沙箱外运行。这两个脚本还要本机装有 Chrome 或 Edge——`tools/cdp.mjs` 先看 `CHROME_PATH`，再按平台找标准安装位置；都找不到时会把所有试过的路径打出来。
